# Reflection Memory V2 — High-Level Idea

## What's Wrong with V1

V1 uses a text diff to describe each editing episode. The memory block injected into
the reflection prompt looks like:

> *"Added: 'Verify all algebraic manipulations and logical deductions...'. Score: 2.00 → 3.00 (ACCEPTED)"*

This is **syntactic noise**. The reflection LLM sees *what words were added*, not *why the
change worked*, *what kind of problems it helped with*, or *what to try next*. V1 is
essentially asking the LLM to re-derive the lesson from a raw text diff — which it often
can't do well from a single terse line.

The AIME light run confirmed this: memory was recording and injecting correctly, but the
injected content was too thin to meaningfully guide future proposals.

---

## The V2 Idea: LLM-Generated Lessons

Instead of diffing text, we make a **small LLM call after every optimization step** to
generate a structured lesson from the episode.

The lesson LLM sees:
- The old prompt (before this iteration)
- The new proposed prompt (after this iteration)
- All per-example evaluation context (feedback strings or raw records from the reflective dataset)
- Aggregate scores before/after + per-example score deltas
- Whether the proposal was accepted or rejected

It produces a **two-part lesson**:

| Field | What it captures |
|-------|-----------------|
| **Intent** | What the edit was trying to achieve |
| **Lesson** | What the outcome reveals — why it worked or failed |

And a **problem category breakdown**:

| Field | What it captures |
|-------|-----------------|
| **Categories succeeded** | Which types of problems the candidate solved correctly |
| **Categories failed** | Which types of problems it still got wrong |

Categories are inferred directly from per-example score deltas and evaluation context (not
constrained to a fixed vocabulary). If the evidence is weak, the LLM uses empty lists.

---

## Problem Category Tracking

AIME (and most benchmark tasks) involve multiple distinct problem types. A prompt may be
strong for number theory but consistently fail on geometry. Without tracking this, the
reflection LLM doesn't know *where* the remaining failures are clustered.

For each optimization step, the lesson LLM looks at the per-example evaluation context and
score deltas, infers the type of each problem, then reports which categories had correct
answers and which had incorrect ones under the new prompt.

This shows up in the memory block as:

> *Iter 3 [ACCEPTED +1.00]*
> *Strong on: number theory, combinatorics*
> *Still failing: geometry, algebra*

Over several iterations, the reflection LLM can see a clear pattern: geometry problems
keep appearing in the "failing" column, and it can specifically target those.

## What the Memory Block Looks Like in V2

```
## Optimization History

### Iter 1 [ACCEPTED +1.00]
Intent: Require explicit step-by-step verification before committing to an answer
Lesson: Adding verification reduced arithmetic errors but didn't help with problems
        requiring creative geometric setup — those require a different strategy
Strong on: number theory, combinatorics
Still failing: geometry, algebra

### Iter 2 [REJECTED ±0.00]
Intent: Strengthen verification language with more comprehensive coverage
Lesson: This is a minor restatement of the Iter 1 change with no new strategy —
        the model already verifies; more emphasis on the same idea doesn't help
Strong on: number theory
Still failing: geometry, algebra, combinatorics

### Iter 4 [REJECTED −1.00]
Intent: Add domain-specific guidance for combinatorics and optimization problems
Lesson: Narrow type-specific advice hurt performance — the model over-specializes
        when the minibatch contains diverse problem types
Strong on: (none — score dropped)
Still failing: geometry, algebra, combinatorics, number theory

IMPORTANT: Do not repeat REJECTED strategies. Build on ACCEPTED ones.
Persistent weak spots: geometry, algebra (failing across multiple iterations)
```

The last line is auto-generated by scanning all entries for categories that appear in
"still failing" more than once — surfacing persistent weak spots without any extra LLM call.

## How This Changes the Optimization Loop

```
V1 loop:
  evaluate → accept/reject → diff(old, new) → store diff → inject diff next iter

V2 loop:
  evaluate → accept/reject → LLM(old, new, all_eval_context, score_deltas, outcome)
  → store lesson+categories → inject rich lesson + category analysis next iter
```

The only addition is one small LLM call per iteration (same model as the reflector,
~600–800 token input, ~150 token output). Latency impact is ~1-2 seconds, which is negligible
when each evaluation iteration takes 15-30 seconds.

If the lesson LLM call fails for any reason (network error, JSON parse failure, missing
keys), V1's `summarize_change()` heuristic is used silently as a fallback. `fallback_used`
is recorded in the `LessonGeneratedEvent` for observability.

---

## Expected Impact

V1 gives the reflection LLM a history of *what text was tried*.
V2 gives it a history of *what was learned and where the gaps are*.

The reflection LLM should:
- Stop repeating failed strategies (clearly marked REJECTED with the lesson why)
- Target unsolved problem categories ("Still failing: geometry for 3 iterations")
- Build more coherently on what worked ("ACCEPTED strategies say to focus on setup")
- Decide its own next move — the memory informs, it does not prescribe

This is the difference between a student reading raw test answers vs reading a tutor's
annotated feedback on what to work on next.

---

## Scope

- One new LLM call per iteration (lesson generation), reusing the reflection LM
- `lesson_lm` parameter allows override to a cheaper model if desired
- No meta-lessons, no lesson consolidation — keep it simple
- V2 is the default behavior when `use_reflection_memory=True` (V1 heuristic used as
  a silent fallback only if the V2 lesson call fails or returns empty output)
