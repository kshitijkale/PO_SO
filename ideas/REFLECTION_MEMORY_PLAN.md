# Implementation Plan: Episodic Memory for GEPA Reflection

## The Problem

Every call to `InstructionProposalSignature.run()` starts from scratch. The reflection LLM sees the current instruction and a minibatch with feedback, but has zero knowledge of what was tried before, what worked, what didn't, or what failure modes have already been diagnosed. It can (and does) propose the same failed mutation twice, oscillate between strategies, or accidentally revert a change that a previous iteration deliberately introduced.

## Where Memory Plugs In

The reflection happens at a single precise location in the codebase:

```
ReflectiveMutationProposer.propose_new_texts()          # reflective_mutation.py:89-136
  → InstructionProposalSignature.run(lm, input_dict)     # instruction_proposal.py
    → InstructionProposalSignature.prompt_renderer(...)   # builds the prompt string
    → lm(prompt)                                          # calls the reflection LLM
    → InstructionProposalSignature.output_extractor(...)  # extracts new instruction
```

The `input_dict` passed to `InstructionProposalSignature.run()` currently has 3 keys:
```python
{
    "current_instruction_doc": str,      # the current component text
    "dataset_with_feedback": list[dict],  # minibatch examples with feedback
    "prompt_template": str | None,        # the reflection prompt template
}
```

Memory must be injected into this path. There are two clean options:

### Option A: Inject Memory Into the Prompt Template (Minimal Changes)

Add a `<memory>` placeholder to the prompt template, and fill it with the memory log before calling `InstructionProposalSignature.run()`. This requires changes only to `ReflectiveMutationProposer`.

### Option B: Add Memory as a New Input Key (Cleaner Separation)

Add `"reflection_memory"` as a 4th key in `input_dict`, and have `InstructionProposalSignature.prompt_renderer()` format and insert it. This requires changes to both the proposer and the signature.

**Recommendation: Option A for a first version** — it's less invasive and keeps the memory logic self-contained in the proposer. Option B is better long-term but touches more files.

## What Gets Stored in Memory

Each memory entry captures one reflection iteration:

```python
@dataclass
class ReflectionMemoryEntry:
    iteration: int
    component_name: str
    # What the LLM diagnosed and proposed
    parent_instruction_snippet: str     # first ~200 chars of the parent instruction
    proposed_instruction_snippet: str   # first ~200 chars of the proposed instruction
    change_summary: str                 # LLM-generated 1-sentence summary of what changed
    # What happened
    score_before: float                 # sum(subsample_scores) before
    score_after: float                  # sum(subsample_scores) after
    accepted: bool                      # did the engine accept this?
    # Failure diagnosis (from the reflective dataset)
    failure_modes: list[str]            # 1-sentence descriptions of each failed example's feedback
```

The `change_summary` is critical — it's a one-line description like "Added step-by-step reasoning instructions" or "Shortened the output format specification". It's generated by a lightweight LLM call (or extracted from the reflection LLM's output with a post-processing prompt).

---

## Data Structure

```python
class ReflectionMemory:
    """Episodic memory of past reflection attempts for the GEPA optimization loop."""

    entries: list[ReflectionMemoryEntry]
    max_entries: int           # rolling window size (default: 20)
    summary_lm: LanguageModel | None  # optional LLM for generating change summaries

    def add(self, entry: ReflectionMemoryEntry) -> None:
        """Add entry, evict oldest if over capacity."""

    def format_for_prompt(self, component_name: str, max_tokens: int = 800) -> str:
        """Render memory relevant to this component as text for the reflection prompt."""

    def get_recent(self, n: int = 5, component_name: str | None = None) -> list[ReflectionMemoryEntry]:
        """Retrieve last n entries, optionally filtered by component."""
```

### Memory Rendering

`format_for_prompt()` produces text like:

```
## Optimization History (last 5 attempts on this component)

Attempt 1 (iter 3): Added chain-of-thought reasoning.
  Score: 2.1 → 3.4 (ACCEPTED)
  Failure modes addressed: "model gave direct answer without showing work"

Attempt 2 (iter 5): Added output format specification (JSON).
  Score: 3.4 → 3.1 (REJECTED)
  Failure modes addressed: "output not parseable"

Attempt 3 (iter 7): Kept chain-of-thought, added "think step by step" phrasing.
  Score: 3.4 → 4.0 (ACCEPTED)
  Failure modes addressed: "model skipped intermediate steps on harder problems"

DO NOT repeat rejected strategies. Build on accepted changes.
```

## The Change Summary Problem

The hardest part is generating the `change_summary` — a one-sentence description of what the mutation actually did. Three approaches:

### Approach 1: Diff-based heuristic (free, approximate)
Compare the old and new instruction text. If short, use the diff directly. If long, truncate to the first changed region.

```python
def _summarize_change(self, old_candidate, new_candidate, components):
    for name in components:
        old, new = old_candidate[name], new_candidate[name]
        if old == new:
            continue
        # Simple: first 100 chars of the diff
        # Could use difflib for a smarter summary
        return f"Changed '{name}': {new[:100]}..."
    return "No changes"
```

### Approach 2: Ask the reflection LLM (1 extra LLM call per iteration)
After the reflection LLM proposes new text, make a cheap follow-up call:
```
"Summarize in one sentence what you changed and why:
Old: {old_text[:300]}
New: {new_text[:300]}"
```

### Approach 3: Extract from reflection output (free, but fragile)
The reflection LLM often explains its reasoning before the ``` block. Parse the text *before* the code block as the change summary. This is fragile but free.

**Recommendation: Start with Approach 1 (diff heuristic) for the first version.** It's deterministic, free, and good enough. Approach 2 can be added later for higher-quality summaries.

## Memory Eviction Strategy

The memory has a fixed capacity (`max_entries`, default 20). When full, evict entries using one of:

1. **FIFO** (simplest): drop the oldest entry
2. **Keep accepted, drop rejected**: accepted entries are more informative; rejected entries mainly say "don't do this again"
3. **Summarize and compress**: when at capacity, use an LLM to summarize the oldest 10 entries into 2-3 bullet points, then drop the originals

**Recommendation: FIFO for v1.** The recency bias is actually desirable — recent failures are more relevant than ancient ones because the candidate has evolved since then.

## Prompt Template With Memory

The memory-aware default prompt template becomes:

```python
default_prompt_template_with_memory = """I provided an assistant with the following instructions:
```
<curr_param>
```

The following are examples of task inputs, assistant responses, and feedback:
```
<side_info>
```

<memory>

Your task is to write a new instruction for the assistant.
Read the inputs carefully and identify the input format and infer detailed task description.
Read all the assistant responses and the corresponding feedback.
If optimization history is provided above, DO NOT repeat strategies that were previously rejected.
Build on strategies that were previously accepted.
Identify all niche and domain specific factual information about the task and include it in the instruction.

Provide the new instructions within ``` blocks."""
```

Note: `<memory>` is replaced with the formatted memory text. If memory is empty, it's replaced with an empty string (the prompt degrades gracefully to the original behavior).

## What NOT to Do

1. **Don't store full instruction texts in memory.** They can be very long. Store snippets (first 200 chars) or diffs.
2. **Don't use memory for the merge proposer.** Merge is syntactic crossover and doesn't use the reflection LLM.
3. **Don't persist memory across runs initially.** Memory is per-run state. Cross-run transfer is a separate research direction.
4. **Don't add memory to callbacks or GEPAState.** Memory is internal to the proposer. It's not part of the optimization state and shouldn't be serialized with checkpoints (unless you want resumability, which is a v2 feature).

## Testing Strategy

1. **Unit test `ReflectionMemory`**: test `add()`, `format_for_prompt()`, eviction, empty memory formatting
2. **Unit test prompt injection**: verify that `<memory>` placeholder is correctly replaced in `propose_new_texts()`
3. **Integration test**: run `optimize()` with `reflection_memory=ReflectionMemory()` on the existing test suite (record/replay) and verify it doesn't break existing behavior
4. **A/B experiment**: run GEPA with and without memory on a benchmark task, compare iterations-to-target-score
